# Длительные исследования и параллельная имплементация

Решение User от2026-10-18: длительные paper-прогоны запускать в отдельных процессах; ожидание их завершения не должно задерживать независимую имплементацию.

1. До старта зафиксировать source/config/criteria; worker использует отдельную DB и byte-identical snapshot, без зависимости от дальнейших изменений рабочего checkout.
2. Запускать один bounded процесс с PID/временем старта,логами,readonly status и самостоятельным итоговым export/verify. Для Windows использовать скрытый процесс,без новых видимых окон.
3. После подтверждения живого PID и первых обработанных наблюдений продолжать независимые задачи. Не держать интерактивный turn открытым часами в ожидании.
4. Монитор проверяет реальное продвижение,сообщает о freeze/error/completion; не рестартует и не меняет окно ради PASS. Статус RUNNING не является результатом проверки.
5. Изменения основного checkout не подмешивать в текущий опыт. Новый код требует отдельного freeze/контрольных проверок. Неизменность snapshot проверять SHA.
6. Зависимые финансовые действия/допуск ждут обязательных результатов и User-приёмки. Это не мешает подготовке кода,тестов,документации и research inputs в разрешённом scope.
7. Не превращать фоновую проверку в бессрочный daemon,автоперезапуск или разрешение реальных ордеров/переводов. После результата отключать монитор конкретного опыта.
