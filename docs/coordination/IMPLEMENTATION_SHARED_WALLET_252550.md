Учётный модуль выплат и исходная спецификация не переписывались.

Цели относятся к decision value D, а не к фактически заблокированной биржевой марже. E=wallet+UPL_LONG+UPL_SHORT, E_trade=E−unpaid_liability, target каждой ноги=E_trade/4. Остаток E_trade−D_LONG−D_SHORT — расчётная составляющая контроллера. Wallet не раскладывается на три независимых актива; маржа уже находится внутри него.

Funding общий: нет виртуальных кошельков и переводов equalizer. ADD доступен из max(0,min(wallet−margin,E−margin)−liability−order_reserve). Это консервативная офлайн-модель, исключающая использование положительного net UPL. Параметры liability/order_reserve задаются явно; соединение с ledger и API ещё отсутствует. Order reserve здесь означает дополнительный резерв, не включённый в margin; повторно передавать уже учтённое обеспечение запрещено.

## Использование

Portfolio.plan_entry возвращает обе стартовые заявки после проверки на копии, либо WAIT без изменения портфеля. В офлайн-исполнителе после исполнения начальной заявки фиксируется leg.initial_units; пример — rebalance/replay.py. Это базовый объём для cap, не текущий растущий объём. Preflight двух заявок не означает атомарного исполнения на бирже.

next_action наблюдает экстремумы и возвращает одно намерение; после fill решение пересчитывается. fill — только симуляционное подтверждение, не отправка заявки. REDUCE на уровне fill может отражать и защитное закрытие с убытком; правило прибыльности применяется planner к ребалансировке. Реальный fill нельзя отбрасывать из-за отсутствия ожидаемой прибыли.

## Ограничения и STOP

Это офлайн-кандидат ядра, не завершённая Binance-интеграция. Нет durable-хранилища торгового состояния/outbox, восстановления после сбоя, UNKNOWN lifecycle, partial fills/cancel race, загрузки exchange filters, risk brackets, account snapshot reconciliation, соединения с учётным ledger, multi-symbol allocation, production TS/stop guards и UI. Идемпотентность receipts действует в памяти, не обеспечивает exactly-once на бирже. Python Decimal имеет конечную контекстную точность; денежное округление реальных Binance-проводок ещё требует спецификации адаптера.

Простая маржа qty*entry/leverage используется только для симуляции обеспечения; actual Binance margin/maintenance/liquidation отдельно не моделируются. Все cash события здесь считаются уже подтверждёнными. Нет сетевых вызовов, ключей и методов создания биржевых заявок. Реальные данные/OOS, производственный replay и сравнение с виртуальными кошельками не выполнены. Нового утверждённого порога Net для Binance нет.

Приёмка текущего результата — User. После отчёта STOP. Следующий предлагаемый этап: согласованный read-only snapshot Binance и офлайн durable lifecycle; live-цикл не переключать до отдельной приёмки.
