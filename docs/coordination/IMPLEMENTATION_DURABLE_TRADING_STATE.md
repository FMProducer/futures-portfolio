## Атомарность и контракты

Одна SQLite БД соответствует одному портфелю/инструменту. Все изменения выполняются через BEGIN IMMEDIATE с synchronous=FULL. Snapshot, revision, запись order и событие commit/rollback вместе. Внешняя отправка не включена в транзакцию SQLite.

prepare сохраняет стабильный client_id, Action, резерв и PREPARED до возможной отправки. План должен соответствовать expected_revision; устаревшая revision отклоняется. Пока есть любое незавершённое намерение, новые намерения и планирование заблокированы. Это намеренно последовательное офлайн-исполнение, а не параллельная торговля двумя ногами.

Переход PREPARED→DISPATCHING выдаёт dispatch_granted=True только при первой фиксации. Повтор того же события возвращает False; другой event id не позволяет заново захватить отправку. Если процесс упал после commit до получения разрешения или ответа провайдера, требуется сверка: повторное предоставление права отправки не выполняется. DISPATCHING после перезапуска сохраняется; вызывающий код может явно перевести его в UNKNOWN. Автоматического сетевого отправителя нет.

UNKNOWN не освобождает резерв. Частичное исполнение UNKNOWN не доказывает статус остатка и не переводит заявку автоматически в OPEN. Полное подтверждённое количество даёт FILLED и нулевой резерв. CANCEL_PENDING допускает приход fill; остаток освобождается только finalize с подтверждённым итоговым количеством, равным уже проведённым fills. Несовпадение блокирует завершение. REJECTED допускается лишь при нулевом исполнении. Доказательства в офлайн-тестах задаёт вызывающий код; их подлинность Store не проверяет.

У ADD резервируются collateral+fee_cap, у REDUCE — fee_cap; закрываемое количество защищено единственным активным намерением. Частичное исполнение пересчитывает резерв остатка пропорционально исходному резерву. price_bound — оценка для резерва, а не обещание биржевой цены. На финальном fill остаток точно равен нулю. Стоимость fill проводится только один раз по trade_id; конфликтующий replay отклоняется. Клиентский идентификатор завершённой заявки повторно не используется.

Если фактический ADD не помещается в моделируемые средства, raw event сохраняется в immutable journal, заявка остаётся UNKNOWN с blocked_trade, резерв удерживается и выдаётся RECONCILIATION_REQUIRED. Фиктивный кредит кошельку и отбрасывание сообщения запрещены. Автоматического исправления такой рассинхронизации ещё нет; это блокирующее состояние, требующее отдельного reconciliation-адаптера. Терминальное завершение до него запрещено.

Сохраняются wallet, позиции/базис/margin/open fees/initial units, liability, order reserve, extrema, receipts, fees, realized и funding. observe сохраняет extrema также при WAIT. initialize не перезаписывает существующий портфель. load возвращает независимый объект; его изменение само по себе не пишет в БД. Входная receipt должна содержать согласованные единицы, один и тот же идентификатор и payload; Decimal строки не заменяют проверку источника.

## Ограничения и следующий этап

Это офлайн outbox с симуляционным исполнением. Нет network dispatcher, cancel sender, биржевых API, аутентификации evidence, загрузки пропущенных fills, account reconciliation, торговли несколькими инструментами, автоматической миграции версии state и интеграции с ledger выплат. Нет поддержки fills после уже принятого противоречащего terminal evidence: требуется отдельное расследование/сверка. Производственная атомарность между двумя биржевыми ногами не обещается. Один активный order ограничивает параллелизм и не обеспечивает полноту начального хеджа.

Резервы и funded check используют текущую упрощённую модель ядра; actual exchange margin/fees/precision требуют отдельной проверки. Файл БД надо хранить и резервировать как runtime state; журнал append-only на уровне триггеров, а не защита от администратора БД. Полного восстановления из независимого удалённого архива здесь нет.

Следующий этап после приёмки: read-only нормализация и сверка Binance snapshot/trades/balances, включая разрешение UNKNOWN. Реальные операции, изменения live config, commit/push не выполнялись. После отчёта STOP.
