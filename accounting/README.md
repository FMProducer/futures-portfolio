# Учётное ядро: первый этап

Изолированный модуль стандартной библиотеки Python 3.11+. Импорт `accounting`
не импортирует торгового бота и не обращается в сеть. Одна SQLite БД соответствует
одной паре project/account. Активы `b_usdt` и `b_gas` пока относятся к одному
условному кошельку сценария, без реальной сети, адреса или контракта токена.

Запуск только фиксированных сценариев из корня checkout:

```powershell
& 'C:/Users/svsma/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe' -m accounting.scenarios.run
```

На другой машине достаточно `python -m accounting.scenarios.run`.
Установка зависимостей бота, `.env`, ключи и запущенный бот не нужны.
Результаты сохраняются в `docs/coordination/accounting_stage1_evidence/`.

Минимальный пример (суммы только строками):

```python
from accounting import Ledger

ledger = Ledger('offline.sqlite3')
ledger.apply('opening:fixed-account', 'initialize', '2026-01-01T00:00:00Z',
             equity='10000', project='fixed-project', account='fixed-account',
             previous_period='2025-12', evidence='fixture:opening')
ledger.apply('transfer:advance', 'advance', '2026-01-01T00:00:00Z',
             evidence='fixture:advance-received')
print(ledger.read())
print(ledger.audit())
```

`apply(key, kind, at, **data)` сериализует операции через `BEGIN IMMEDIATE`.
Все effective timestamps задаются в UTC и не убывают. Повтор старого события
проверяется до проверки времени. Повтор точного запроса возвращает исходный
результат, включая исходное состояние; актуальное состояние даёт `read()`.
Изменённый запрос под тем же ключом вызывает `Conflict`. Для внешних движений
`evidence` также является уникальным естественным ключом: повтор под другим
локальным ID возвращает исходный результат, изменение данных вызывает конфликт.
Для реального адаптера ключ должен включать провайдера, аккаунт, сеть,
транзакцию, индекс события и тип проводки. Общая ссылка на документ вместо
уникального идентификатора движения не подходит.

Основные команды и поля приведены непосредственно в воспроизводимых сценариях
`scenarios/test_ledger.py`. Типы команд:

| Команды | Назначение |
|---|---|
| initialize, advance, fund_b | Инициализация, подтверждённый аванс 200, внешнее финансирование Б |
| snapshot, user_flow, close | Фиксированный согласованный Equity, внешний поток А, закрытие месяца |
| reserve_payout, unknown_payout, settle_payout | Резерв, неопределённость, конечный расчёт выплаты |
| subscription, calendar, gas_protection | Стоимость цикла, экземпляр обязательства, защита газа |
| reserve_order, unknown_order, settle_order | Резерв и расчёт покупки, карточного аванса или обмена на газ |
| card_purchase, card_return, refund | Подтверждение карточного расхода, возврат аванса, возврат расхода |

Физические количества газа и комиссий другого актива сохраняются отдельно от
оценки USDT. У `settle_payout` поле `fee` — полная комиссия в эквиваленте USDT;
не-USDT части задаются `fee_lines` с asset, quantity, price, source. Остаток fee
относится к USDT. `debit` — совокупное уменьшение Equity в том же эквиваленте,
`received` — физическое поступление USDT. Суммы должны быть полностью сверены.
Несверенная частичная отправка остаётся UNKNOWN; отдельные частичные выплаты
допускаются как самостоятельные полностью сверенные заявки.

Успешная покупка газа требует `gas_received`; вся покупная стоимость переносится
в газ, а расходом признаются комиссии. Газ и USDT фиксированного сценария
пополняются только явными событиями. Фактические комиссии сверх caps проводятся,
даже если вызывают отрицательный расчётный остаток Б: это дефицит для сверки,
а не разрешение на овердрафт. Новая заявка проверяет физическое покрытие заново.

Возврат в этой версии — подтверждённое поступление USDT, связанное с конкретным
расходом. Возврат газа в исходном активе, частичные расчёты с расхождением,
автоматическая конвертация карточных валют и реальные сетевые события здесь
не моделируются. Покрытие базовых расходов распределяется в стабильном порядке
expense ID; внутри связанного расхода возврат сначала уменьшает непокрытую часть,
затем создаёт credit. Эти правила разнесения явно доступны для приёмки.

Ограничение числового API: входные суммы имеют не более 28 значащих цифр и
модуль десятичного порядка не более 18. Рабочая точность 80 цифр; непредусмотренная
потеря точности вызывает исключение. R округляется HALF_EVEN до цента.
Периодические дроби Normalized_30 округляются вверх до 18 дробных знаков,
чтобы не занизить защиту резерва. Другие суммы не округляются до цента.

`audit()` сравнивает проекцию с последним событием, суммы дельт регистров и
SQLite integrity_check. SQLite восстанавливает незавершённую транзакцию при
повторном открытии. Повторная инициализация запрещена. Изменение проекции
обнаруживается перед следующей записью; автоматического ремонта произвольно
повреждённых файлов нет. Журнал защищён от UPDATE/DELETE триггерами; это не
защита от владельца файла БД, способного удалить триггеры или сам файл.

`valid=True` и `evidence` обозначают входы фиксированного сценария, а не
проверку биржевой согласованности. Исторические данные нельзя подменять текущими:
несвоевременные события отклоняются, несогласованное закрытие вызывает
`PENDING_DATA` в исключении без проводок. Долговечная очередь PENDING_DATA,
историческая пересборка и согласование снимков относятся к следующей интеграции.

Не подключать этот модуль к существующему фьючерсному исполнителю без отдельного
согласования торгового контракта и проверки адаптера Binance. Первый этап
завершается отчётом и приёмкой Пользователя.
